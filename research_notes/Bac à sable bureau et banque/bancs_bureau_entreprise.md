## WorkBench (arXiv 2405.00823) : données, évaluation, volumes, enjeux

### Takeaway
WorkBench est le meilleur candidat « bureau » : tâches avec actions attendues explicites (`outcome` = liste d'appels d'outils avec arguments), 947 écritures attendues sur 690 tâches, MIT, maintenu (dernier commit 2026-08-18), installable avec `uv sync` sans Docker, et des traces Claude déjà publiées par tâche. Réserve majeure : le verdict officiel est par tâche (comparaison d'état final), pas par appel ; un verdict par appel est reconstructible hors ligne mais n'est pas fourni.

### Cited Findings
- [VÉRIFIÉ] 690 tâches réparties en 6 fichiers `data/processed/tasks_and_outcomes/*.csv` : analytics 120, calendrier 110, CRM 80, email 90, gestion de projet 80, multi-domaine 210. Colonnes : `task`, `outcome`, `base_template`, `chosen_template`, `domains`. Exemple (email) : `task`="Delete my last email from nadia", `outcome`=`['email.delete_email.func(email_id="00000479")']`. — dépôt olly-styles/WorkBench, données lues
- [VÉRIFIÉ] Comptage de mon script sur la colonne `outcome` (ground truth v2 courante) : 947 appels d'écriture attendus au total. Répartition par outil : CRM.delete_customer 174, CRM.update_customer 131, analytics.create_plot 106, project_management.update_task 91, calendar.delete_event 86, email.send_email 79, calendar.create_event 74, project_management.create_task 56, email.forward_email 51, calendar.update_event 30, email.delete_email 29, CRM.add_customer 20, email.reply_email 20. `project_management.delete_task` : 0 attendu (existe comme outil).
- [VÉRIFIÉ] Distribution du nombre d'écritures attendues par tâche : 0 écriture : 122 tâches ; 1 : 416 ; 2 : 88 ; 3 : 23 ; 4 : 14 ; 5 : 2 ; 6 : 5 ; 7 : 3 ; 8 : 4 ; 9 : 3 ; 10 : 2 ; 11 : 6 ; 12 : 2. Les 122 tâches à zéro action sont des « pièges de condition » : dans le fichier multi-domaine, 41 ont `outcome` = `[]` (ex. « si on n'a pas parlé à Jessie Thomas depuis deux semaines, réserve une réunion… » dont la condition est fausse) ; les 81 autres tâches vides sont dans d'autres fichiers (non ventilées). Utile pour mesurer la sur-action.
- [VÉRIFIÉ] 26 outils : 14 « avec effets de bord » (`tools_with_side_effects` dans `src/tools/toolkits.py`) : calendar create/delete/update_event ; email send/delete/forward/reply ; analytics.create_plot ; project_management create/delete/update_task ; CRM update/add/delete_customer ; plus 13 outils de lecture/recherche. Le typage lecture/écriture est donc explicite dans le code.
- [VÉRIFIÉ] Évaluation (`src/evals/evaluation.py`) : `is_correct` exécute les actions prédites et les actions attendues sur un bac à sable reset, puis compare les DataFrames d'état (`_states_match`, comparaison indépendante de l'ordre). `has_side_effects` = l'état a changé par rapport à l'initial ET la tâche n'est pas correcte (les plots sont exclus, `SIDE_EFFECT_STATE_FIELDS` = calendar_events, emails, project_tasks, crm_data). `is_exact_match` existe aussi. Aucun juge LLM. Verdict officiel : par tâche, pas par appel.
- [VÉRIFIÉ] `data/results/item_level_results.csv.gz` : une ligne par (run, tâche) avec `ground_truth_actions`, `predicted_actions`, `num_ground_truth_actions`, `num_predicted_actions`, `correct`, `unwanted_side_effects`, `exact_match`, `wrong_email`, `no_actions`, `error`. Contient pour Claude : claude-fable-5, claude-opus-4.8, claude-sonnet-4.6, claude-haiku-4.5 (690 lignes chacun, `revisited_2026`) et claude-2 (2024). Permet de calculer hors ligne un verdict par appel (chaîne d'appel prédit présente dans l'ensemble attendu) sans rien rejouer. Pas de runs Claude 5.5 : ceux de la recherche devront être faits.
- [VÉRIFIÉ] Enjeux couverts : suppressions (CRM.delete_customer 174, calendar.delete_event 86, email.delete_email 29), communication externe irréversible (send_email 79, forward 51, reply 20), modifications de données (CRM.update, task update), création. Absents : argent/paiement, changement de permissions/partage, publication. Le README parle d'« envoi à la mauvaise personne » comme erreur irréversible subsistante, et le flag `wrong_email` existe dans l'item-level. Les trois niveaux d'enjeu devront être assignés par nous par type d'outil (aucun champ d'enjeu dans les données).
- [VÉRIFIÉ] Licence MIT (Copyright 2024 Mindsdb). Dernier commit : 2026-08-18 « Merge pull request #56 ». Python 3.12+ et `uv sync --frozen` ; aucune infrastructure (bases CSV en mémoire). Appel LLM via API compatible OpenAI (OpenRouter ou clés directes dont ANTHROPIC_API_KEY, `claude-*` dans `MODEL_REGISTRY`). Boucle : 26 outils, 20 pas max, température 0 quand possible.
- [VÉRIFIÉ, estimations de l'auteur] Coût par tâche estimé (Table 1 de `retro/main.pdf`, tokens ≈ longueur/4, ~7 000 tokens de prompt+schéma renvoyés à chaque appel, sans cache, donc majorant) : Claude Fable 5 0,355 $ ; Opus 4.8 0,182 $ ; Sonnet 4.6 0,105 $ ; Haiku 4.5 0,034 $. Complétion / effets de bord : Fable 5 97,7 % / 1,9 % ; Opus 4.8 96,2 % / 2,5 % ; Sonnet 4.6 88,3 % / 8,8 % ; Haiku 4.5 74,8 % / 16,7 %. Coût d'un passage complet de 690 tâches ≈ 0,034 × 690 ≈ 23 $ (Haiku) à ≈ 72 $ (Sonnet 4.6), ≈ 126 $ (Opus 4.8) : calcul de moi à partir de ces chiffres, à confirmer.
- [VÉRIFIÉ] Défauts d'annotation connus, documentés par les auteurs eux-mêmes (retro, annexe A.1) : décalage d'un jour dans « last N days » ; 56 tâches de graphiques dont la date de fin était refusée ; incohérences énoncé/réponse (« more than » toujours affiché, réponse parfois « less than ») ; bug idxmin ignorant les personnes à zéro tâche ; une tâche de report violant la règle des 18 h ; 10 tâches d'envoi d'email échouant sur `\n` littéral ; comptages insolubles (cap de 5 résultats). Impact : 56 tâches (8 %) au minimum, 90 à 95 (≈ 14 %) en élargissant ; GPT-4 passe de 49 % à 57 % sur la version corrigée. Ground truth versionné (v1, v2026-05-17, v2026-05-19, courant). Reste un « plancher dur » de tâches à vérité ou énoncé discutable (retro). Aucune analyse indépendante d'erreurs d'étiquettes sur WorkBench trouvée par recherche web.
- [ARTICLE/README] Reconnaissance : papier arXiv 2405.00823 (2024, MindsDB). Je n'ai trouvé aucune fiche modèle Anthropic/OpenAI/Google ni classement officiel citant WorkBench ; la « reconnaissance » est faible, la réévaluation 2026 est faite par l'auteur original. [Aucune source de laboratoire trouvée]

### Inferences
- 947 écritures attendues restent un volume modeste pour une règle par type d'action et par enjeu : 13 types d'outil, dont 6 types ont ≥ 74 écritures, 3 ont ≤ 30 (update_event 30, add_customer 20, reply 20). Les cellules type × enjeu seront maigres.
- Avec des modèles à 96-98 % de complétion, les échecs sont rares (≈ 2 % d'effets de bord pour Opus 4.8 et Fable 5) : peu de signal négatif par cellule pour Opus ; Haiku (16,7 %) et Sonnet 4.6 (8,8 %) en fournissent bien plus.
- Un seul épisode = une tâche, 1 à 12 écritures ; le verdict par appel par appariement de chaînes (action prédite ∈ actions attendues) est cohérent avec le scoreur car les actions sont des chaînes d'appels Python, mais l'ordre et les doublons (envoyer deux fois) demandent une règle propre.

### Gaps
- Je n'ai pas ventilé les 81 tâches à zéro action hors du fichier multi-domaine ni vérifié les corrections par tâche entre v1 et v2.
- Pas de mesure faite du coût réel avec Claude 5.5 (aucun appel API autorisé).

## OfficeBench, CRMArena / CRMArena-Pro, WorkArena, EnterpriseBench et autres bancs 2025-2026

### Takeaway
Aucun de ces bancs ne donne des appels attendus par tâche vérifiables sans juge, hormis (avec réserves) Gaia2/ARE et EnterpriseBench (juge LLM, donc exclu). OfficeBench, CRMArena et WorkArena notent un état final ou une réponse ; AppWorld et Toolathlon notent un état final par tests unitaires ; Gaia2 est le seul à valider chaque action d'écriture, mais avec un vérificateur LLM pour le texte libre.

### Cited Findings
- OfficeBench (arXiv 2407.19056) [VÉRIFIÉ] : 300 fichiers de sous-tâches `tasks/*/subtasks/*.json` (167 dossiers de tâches), champ `evaluation` = liste de fonctions (`evaluate_contain`, `evaluate_file_exist`, `evaluate_excel_cell_value`, `evaluate_calendar_no_overlap`, `evaluate_diff_contain_text`, …) appliquées aux fichiers de sortie ; pas d'appels attendus. Licence Apache 2.0, dernier commit 2026-03-31, exécution via image Docker (README `--docker_name`, dossier `docker/`). Verdict : par tâche, état final, non adapté.
- CRMArena / CRMArena-Pro (Salesforce) [VÉRIFIÉ] : métriques dans `crm_sandbox/agents/utils.py` = exact match, F1, BLEU, ROUGE ; `reward_metric` par tâche incl. `fuzzy_match` ; dépôt livre des bases locales (`local_data/*.db`) mais README exige les identifiants d'une org Salesforce et des clés API ; licence CC BY-NC 4.0 (usage non commercial : question à trancher pour un projet de recherche) ; dernier commit 2026-11-03. Tâches = réponses (requête, politique, workflow) plutôt qu'écritures par appel. [ARTICLE/TIERS, arXiv 2505.18878] 19 tâches, 4 compétences ; environ 58 % en un tour et 35 % multi-tours pour les meilleurs agents ; workflow > 83 % en un tour. Non adapté au verdict par écriture.
- WorkArena / WorkArena++ (ServiceNow) [VÉRIFIÉ/README] : nécessite une instance ServiceNow (PDI) ; README : L1 « 19 912 instances uniques tirées de 33 tâches », WorkArena++ 682 tâches ; navigation navigateur (BrowserGym) ; Apache 2.0 ; dernier commit 2026-09-28. Validation par état de la plateforme, pas par appels ; agents navigateur coûteux. Non adapté.
- EnterpriseBench (Fujitsu, EMNLP 2025, arXiv 2510.27287) [VÉRIFIÉ] : `Evaluate/evaluate.py` = « LLM-as-judge » (score 1-5) ; MIT ; dernier commit 2026-09-15. Les données contiennent pourtant des `ground_truth.expected_tool_sequence`, `required_tools`, `reward_checkpoints` (outil, opération `delete`/`update`…, `input_bindings`) : `training_tasks.json` 2 000 tâches, `training_tasks_new.json` 900, `Task_Generation/tasks.json` 451. [ARTICLE/TIERS] 500 tâches (RH, finance, IT, ingénierie), 41,8 % de complétion pour le meilleur modèle. Verdict officiel par juge LLM, donc exclu tel quel ; les checkpoints pourraient être rejoués par comparaison exacte mais cette voie n'est pas supportée et les bases sont synthétiques (qualité des étiquettes non auditée, pas d'analyse trouvée).
- TheAgentCompany [VÉRIFIÉ] : dernier commit 2025-11-17 (plus de 11 mois : possiblement dépassé) ; README exige Docker/compose et « 30+ GB of free disk space » ; 175 dossiers de tâches dans `workspaces/tasks` ; licence MIT. Évaluation par points de contrôle par tâche (certains jugés par LLM selon l'article, non revérifié ici). Confirme le jugement antérieur : trop lourd.
- Gaia2 / ARE (Meta, arXiv 2602.11964, ICLR 2026) [VÉRIFIÉ pour le dépôt] : dépôt facebookresearch/meta-agents-research-environments, licence MIT, dernier commit 2026-09-30 ; README : « 800 scenarios across 10 universes » ; `pip install meta-agents-research-environments` ; code de vérification dans `are/simulation/validation/event_judge.py` (`AgentEventJudge`) avec `per_tool_soft_checker_types` et un registre `CheckerType.llm_checker` appliqué à des champs libres (`title`, `description`, `location`, `content`, `subject`), donc les champs textuels sont jugés par LLM (moteur LiteLLM configurable), tandis que les identifiants relèvent de comparaisons strictes. [ARTICLE, page arXiv] « Each scenario is paired with a write-action verifier, enabling fine-grained, action-level evaluation » ; licence du papier CC BY 4.0. [TIERS, non confirmé] ensemble minimal d'actions d'écriture d'oracle, succès si toutes appariées, accord 0,98 avec humains sur 450 trajectoires ; le chiffre « 1 120 scénarios » que je croyais n'a pas été retrouvé : la source est 800 (README ; table de Toolathlon : « 800 tasks, 12 applications »). Le jeu de scénarios lui-même est sur Hugging Face, non cloné ici. Verdict par écriture : oui, mais avec juge LLM partiel pour les textes. Enjeux : email, calendrier, contacts, messagerie (non vérifié en détail) ; pas d'argent.
- AppWorld [VÉRIFIÉ pour le dépôt] : licence Apache 2.0, dernier commit 2026-09-03, `pip install appworld`, serveur avec ou sans Docker (README) ; données de tâches téléchargées à part (non clonées). [ARTICLE/TIERS, arXiv 2407.18901] 9 applications, 457 API, 750 tâches (250 scénarios), évaluation par tests unitaires d'état avec dommages collatéraux ; meilleur modèle ≈ 49 % (normal) et ≈ 30 % (challenge) dans l'article d'origine (obsolète). Domaine : applis grand public (Venmo, Spotify, courriel, notes, tâches), argent simulé via Venmo ; verdict par état/tâche, pas par appel.
- Toolathlon [VÉRIFIÉ pour le dépôt] : 110 dossiers sous `tasks/` (108 tâches selon l'article), conteneur par tâche, Docker/Podman requis ; variante sans Docker `README_nodocker.md` ; « strongly suggest » une machine Linux ; 592 Mo ; dernier commit 2026-08-06 ; pas de fichier LICENSE à la racine (licence à confirmer). Contrôle par script de vérification d'état par tâche. [ARTICLE/TIERS] Claude-4.5-Sonnet 38,6 % dans l'article ; classements tiers (benchlm.ai, llm-stats) montrent Claude Opus 4.8 à 59,9 % ; tous les scores de llm-stats sont auto-déclarés. Lourd, non adapté.

### Inferences
- Parmi les bancs « bureau », seuls WorkBench (écritures typées + chaînes d'appels attendues + sans juge) et Gaia2 (vérificateur d'actions d'écriture) correspondent au critère (a) ; Gaia2 viole « sans juge LLM » pour les champs textuels.
- EnterpriseBench possède des séquences d'outils attendues mais l'évaluateur officiel est un juge LLM : exclu sauf à réécrire l'évaluation, ce qui sort du cadre « banc public tel quel ».

### Gaps
- Je n'ai pas obtenu le détail de Gaia2 (répartition par capacité, outils, coût, accord humain) : le PDF n'était pas lisible via l'outil de lecture. À vérifier dans le jeu Hugging Face et l'annexe.
- Aucun papier d'erreurs d'étiquettes trouvé pour OfficeBench, CRMArena(-Pro), WorkArena, EnterpriseBench, Gaia2, AppWorld par ma recherche web (une seule requête dédiée, résultats hors sujet).
- Coût par épisode avec Claude : seul WorkBench en publie une estimation.

## Quel candidat unique pour le profil « bureau » ?

### Takeaway
WorkBench (version « Revisited » 2026, ground truth v2 courante). Faiblesses principales : verdict par tâche à reconstruire en verdict par appel, 947 écritures seulement et répartition déséquilibrée, enjeux limités (pas d'argent ni de permissions), saturation par les modèles de pointe, jeu à 8-14 % de tâches corrigées, peu de reconnaissance externe.

### Cited Findings
- Critères (a) à (g) pour WorkBench : voir section 1 (tous [VÉRIFIÉ] sauf (f), aucune source).
- Alternative secondaire : Gaia2/ARE (MIT, 800 scénarios, vérificateur d'actions d'écriture, installable par pip) — mais juge LLM pour le texte libre et détails non vérifiés. [VÉRIFIÉ pour licence, dépôt, code du vérificateur ; reste ARTICLE]

### Inferences
- Faiblesses chiffrées de WorkBench : 122 tâches sur 690 (18 %) sans écriture attendue ; seulement 3 types d'enjeu bien représentés (suppression, envoi externe, modification) ; échecs d'Opus/Fable ≈ 2 % d'effets de bord donc peu de négatifs ; ajouter des runs Haiku/Sonnet 5.5 pour obtenir du contraste.
- Recommandation : prendre WorkBench comme banc bureau principal et regarder Gaia2 en complément pour couvrir messagerie/contacts avec un second type de verdict, après lecture directe du jeu Hugging Face.

### Gaps
- Pas d'essai d'exécution (interdit). Le coût réel avec Claude 5.5 reste à mesurer avec le journal de traces (`--log_traces`).
