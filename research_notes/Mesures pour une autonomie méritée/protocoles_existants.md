# Protocoles, standards et projets existants : délégation progressive / atténuée / sur preuves pour agents IA (état au 2026-11-04)

Méthode : ~17 appels WebSearch/WebFetch le 2026-11-04. Légende : [F]=page primaire lue en entier/en partie ; [S]=résumé de moteur de recherche, page non ouverte ; [NV]=non vérifié. Aucun chiffre inventé.

## Q1. Autorisation d'agent dans les protocoles d'agents (MCP, A2A, AP2, cartes, IETF/OIDF, Entra Agent ID)

### Takeaway
Tous expriment des permissions statiques ou à portée bornée (scopes, mandats plafonnés, jetons de carte avec plafond). Aucun ne fait croître/décroître les droits d'après le bilan mesuré de l'agent. Révocation et audit : présents mais au niveau transport/jeton, pas au niveau « registre de preuves → promotion ».

### Cited Findings
- **MCP authorization** — spec datée 2026-07-28, auth OPTIONNELLE, basée OAuth 2.1 (draft-ietf-oauth-v2-1-13), RFC 8707 (resource), 9728, Client ID Metadata Documents ; DCR déprécié. Ouvert, livré. — [F] [MCP spec 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization)
  - Permissions : scopes OAuth. « Step-up » : le serveur répond 403 `insufficient_scope` + `scope=`, le client redemande l'union des scopes ; « least privilege » en SHOULD ; `scopes_supported` = jeu minimal, le reste demandé « incrementally ». C'est un élargissement déclenché par le BESOIN d'une opération, pas par un historique de preuves. Pas de plafond, pas de ledger, pas de rétrogradation définis. Révocation : non traitée dans le texte lu (hors tokens expirés → 401). Testé terrain : largement déployé (écosystème MCP), mais pas vérifié ici par source chiffrée.
- **A2A (Agent2Agent)** — hébergé Linux Foundation ; Protobuf `a2a.proto` normatif ; AgentCard déclare `securitySchemes` (API key, HTTP, OAuth2, OIDC, mTLS) et `securityRequirements` ; v1.0 en 2026 selon Tyk. Ouvert, livré. — [S] [a2a-protocol.org llms-reference](https://a2a-protocol.org/llms-reference.txt) ; [S] [Tyk](https://tyk.io/blog/a2a-protocol/) ; [S] [Gravitee](https://www.gravitee.io/a2a-protocol.html) : la spec définit comment l'identité est affirmée, pas ce qu'elle peut faire (autorisation = déploiement). Pas de niveaux, ledger ni révocation natifs.
- **AP2 (Agent Payments Protocol)** — lancé sept. 2025 par Google + 60+ partenaires, extension d'A2A ; v0.2 ; licence Apache 2.0 ; normalisation poursuivie au FIDO Alliance (groupes Agentic Authentication / Payments). Ouvert, livré en échantillons publics, « émergent ». — [F] [ap2-protocol.org](https://ap2-protocol.org)
  - Mandats : Checkout Mandate (open/closed) et Payment Mandate (open/closed) ; « open » = contraintes (budget, instruments autorisés) pour exécution autonome ; « closed » = autorisation d'un montant précis. VDC signés, chaînés = « piste d'audit non répudiable ». Plafonds/expiry détaillés non lus sur cette page ; révocation non couverte sur cette page. Ancien vocabulaire (Intent/Cart/Payment mandate, plafond de prix, TTL) vu en sources secondaires : [S] [Analytics Vidhya / Worldline](https://docs.connect.worldline-solutions.com/documentation/ConnectAI/agent-payments-protocol-ap2). Revolut annonce compatibilité janv. 2026 [S] ([stellagent](https://stellagent.ai/insights/ap2-agent-payments-protocol)). Pas de promotion/rétrogradation sur preuves.
- **Cartes (Visa Intelligent Commerce, Mastercard Agent Pay)** — jeton tokenisé délégué avec plafonds de dépense, catégories marchands, invites d'approbation en temps réel ; Mastercard : « Agentic Token » lié à un agent + une politique, révocation, supervision émetteur/réseau. Propriétaire (réseaux privés), livré (pilotes/rails). — [S] [PYMNTS Visa](https://pymnts.com/visa/2025/visa-powers-ai-shopping-agents-with-intelligent-commerce-payment-rails) ; [S] [Crossmint comparatif](https://crossmint.com/learn/agent-card-payments-compared) ; [S] [American Banker](https://www.americanbanker.com/payments/news/visa-mastercard-launch-payments-for-agentic-ai). Sources divergent sur réutilisable vs usage unique ; « la plupart des achats exigent encore une approbation humaine mi-2026 » (CoinGecko, [S] [lien](https://www.coingecko.com/learn/top-agent-cards-ai-payments)). Limites fixées par l'humain, pas adaptées aux preuves. Interop inter-réseaux : non.
- **IETF OAuth « On-Behalf-Of User » pour agents** — draft-oauth-ai-agents-on-behalf-of-user (WSO2 : Senarath, Dissanayaka), v00 mai 2025, v02 août 2025 ; `requested_actor` / `actor_token`, claim `act` ; trace user/client/agent. Draft individuel, expiré (v02 : 27 fév. 2026), aucune adoption confirmée. — [F/S] [datatracker v02](https://datatracker.ietf.org/doc/html/draft-oauth-ai-agents-on-behalf-of-user-02) ; [S] [NHIMG](https://nhimg.org/articles/oauth-on-behalf-of-for-ai-agents-clarifies-delegated-identity/). Exprime l'identité/chaîne de délégation, pas la progression.
- **OpenID Foundation** — livre blanc « Identity Management for Agentic AI » (AI Identity Management Community Group), 2025-10-07, arXiv:2510.25819. Constat : cadres actuels OK pour agents simples, tendus pour délégation récursive, confiance inter-domaines, échelle ; recommande profils interopérables d'OAuth/OIDC, éviter systèmes d'identité propriétaires, traiter les agents comme acteurs IAM avec cycle de vie. Pas un protocole. — [S] [openid.net](https://openid.net/new-whitepaper-tackles-ai-agent-identity-challenges/) ; [S] [arXiv](https://arxiv.org/abs/2510.25819). Aucun suivi 2026 trouvé.
- **Microsoft Entra Agent ID** — propriétaire, livré (docs dites GA sur « what's new », certaines pages encore « preview » : statut à confirmer). Accès conditionnel appliqué aux identités d'agents ou aux « blueprints » (classe d'agents), politique basée sur le risque ID Protection (ex. blocage d'agents autonomes à risque moyen/élevé), désactivation d'identités d'agents. Licence : Entra P1/P2 + Agent 365. — [S] [Learn : CA for agents](https://learn.microsoft.com/en-us/entra/identity/conditional-access/agent-id) ; [S] [what's new](https://docs.azure.cn/en-us/entra/agent-id/whats-new-agent-id) ; [S] [disable agent identities](https://learn.microsoft.com/en-in/entra/agent-id/disable-agent-identities). Seul cas avec « risque » dynamique qui BLOQUE (démotion binaire) ; pas de promotion sur preuves ni de registre ouvert.
- **Okta, OIDC-A** : mentionnés en commentaire secondaire seulement — [S] [thepaypers](https://thepaypers.com/fraud-and-fincrime/news/openid-foundation-warns-of-security-flaws-in-ai-agent-identity) ; [NV] contenu non lu.

### Inferences
- Le « step-up » MCP est le plus proche d'un élargissement progressif, mais il est réactif (par opération), accordé par le consentement utilisateur, sans mémoire de la fiabilité passée.
- Les plafonds/mandats (AP2, cartes) montrent que « plafond + expiration + révocation » est un acquis ; le seuil de ces plafonds est fixé par l'humain.

### Gaps
- Texte exact des mandats AP2 (caps, expiry, révocation) non lu (sous-pages spec). Statut GA/preview exact d'Entra non tranché. Texte primaire d'A2A non lu (résumés). Pas de vérification des chiffres d'adoption.

## Q2. Jetons de délégation/atténuation et moteurs de politiques (RAR, GNAP, UCAN, macaroons, Biscuit, OPA, Cedar)

### Takeaway
L'atténuation (rétrécir seulement) est bien outillée et en cours de standardisation pour les agents ; l'élargissement par preuves est volontairement exclu des invariants (« jamais élargir »). Les moteurs de politiques peuvent exprimer plafonds/temps/conditions, mais l'élargissement progressif se fait en réémettant une politique, hors du moteur.

### Cited Findings
- **IETF draft « Attenuating Authorization Tokens for Agentic Delegation Chains »** (draft-niyikiza-oauth-attenuating-agent-tokens-01, N. A. Niyikiza, Tenuo, 2026-06-15, expire 2026-12-17, groupe OAuth, voie Standards Track visée, PAS adopté). JWT + `authorization_details` RFC 9396 type `attenuating_agent_token` ; contraintes `exact/range/one_of/not_one_of/contains/subset/wildcard/all/any` ; invariants : TTL enfant ≤ parent, profondeur de délégation croissante/max décroissant, « authority can stay the same or narrow, but never widen », preuve de possession par invocation, dérivation hors ligne. Révocation (§8.9) et statut d'implémentation (annexe E) : sections non lues. — [F] [IETF draft](https://www.ietf.org/archive/id/draft-niyikiza-oauth-attenuating-agent-tokens-01.html) (50 661 derniers caractères non lus). Citation clé : RAR « does not define how a token holder can produce a narrower token ».
- **IETF « Agent Delegation Chain »** (draft-asor-wimse-agent-delegation-chain-00/-01) : profil des JWT OAuth, autorité en RAR, chaque délégation liée au parent par référence cryptographique ; ses auteurs disent viser une convergence avec le précédent. — [S] [draft -01](https://www.ietf.org/ietf-ftp/internet-drafts/draft-asor-wimse-agent-delegation-chain-01.txt). Dates exactes (résumé : août 2026) non confirmées.
- **Macaroons / Biscuit / UCAN** : macaroons = HMAC chaîné, atténuation sans l'émetteur, mais tout vérificateur peut forger (secret partagé) ; Biscuit = asymétrique, Datalog, format protobuf hors IETF ; UCAN = JWT imbriqués + DID, capacités = URI plates sans conditions/budget/temps (critique de papiers), taille quadratique selon la profondeur. — [S] [arXiv 2609.06500 CAPMAS](https://arxiv.org/pdf/2609.06500) ; [S] [arXiv 2603.24775 AIP](https://arxiv.org/pdf/2603.24775) ; [F] draft Niyikiza ci-dessus (comparaison). Revocation décentralisée = problème ouvert ([S] [emergentmind](https://www.emergentmind.com/open-problems/revocation-in-decentralized-agent-delegation-chains)). Ouverts ; production d'agents : papiers/prototypes, pas de déploiement vérifié ici.
- **AIP : Agent Identity Protocol** (arXiv 2603.24775, mars 2026) et **CAPMAS** (arXiv 2609.06500) : propositions académiques, jetons à invocation liée (JWT mono-saut, chaînes Biscuit multi-saut). — [S] [alphaxiv AIP](https://www.alphaxiv.org/abs/2603.24775.md). [NV] pas de tests terrain constatés.
- **Google DeepMind « Intelligent AI Delegation »** (arXiv 2602.11865, fév. 2026) : cadre de délégation, jetons de capacité de délégation (macaroons, selon un blog éditeur), disjoncteurs de révocation, distinction confiance (croyance contextuelle) vs réputation (historique de performance). Papier de position, pas de protocole livré. — [S] [arXiv](https://arxiv.org/pdf/2602.11865.pdf) ; [S] [SatGate (source commerciale)](https://satgate.io/blog/deepmind-intelligent-delegation-satgate). Section/détails à vérifier dans le PDF.
- **GNAP (RFC 9635)** : octobre 2024, éd. Justin Richer, délégation d'autorisation, non compatible OAuth 2.0 — [S] [rfc9635 xml](https://ietf.potaroo.net/rfc/rfc9635.xml). Aucun usage agent trouvé.
- **RFC 9396 (RAR)** : existence confirmée via le draft Niyikiza (profil RAR, `authorization_details`) ; texte RFC non lu — [F, indirect] voir lien draft.
- **Cedar** (AWS) : permit/forbid, principal-action-resource + `when/unless` pouvant référer aux paramètres d'outil et aux tags de jeton OAuth ; forbid l'emporte, refus par défaut. Utilisé dans Bedrock AgentCore pour contrôler l'accès des agents aux outils. Open source (licence non relue ici [NV]) ; livré. — [S] [AWS AgentCore Cedar](https://docs.aws.amazon.com/de_de/bedrock-agentcore/latest/devguide/policy-understanding-cedar.html) ; [S] [API CedarPolicy](https://docs.aws.amazon.com/bedrock-agentcore-control/latest/APIReference/API_CedarPolicy.html).
- **OPA / Rego** : non recherché dans cette session — [NV].

### Inferences
- Plafonds, TTL, listes d'arguments : exprimables aujourd'hui (draft Niyikiza, Cedar). Plafond cumulatif/budget dépensé (état) : nécessite un état externe ; non démontré dans les sources lues.
- L'élargissement par preuves = « émettre un nouveau jeton/politique plus large », décision hors jeton ; aucune spec ne la normalise.

### Gaps
- Sections révocation/implémentation du draft Niyikiza non lues. OPA, Biscuit/UCAN specs primaires, texte RFC 9396 non consultés. Pas de preuve de GNAP en contexte agent.

## Q3. Autonomie méritée, adaptative ou fondée sur la réputation

### Takeaway
Idées et prototypes abondants (papiers, blogs, produits) ; un seul patron complet (AWS « graduated autonomy ») mais conceptuel, non testé en production dans le texte. Aucun standard ouvert interopérable.

### Cited Findings
- **Feng, McDonald, Zhang, « Levels of Autonomy for AI Agents »** — EXISTE : arXiv:2506.12469, 14 juin 2025, v2 28 juil. 2025, U. Washington. 5 niveaux par rôle utilisateur (opérateur, collaborateur, consultant, approbateur, observateur) ; autonomie = choix de conception distinct de la capacité ; « certificats d'autonomie » émis par un tiers gouvernant, fondés sur des « autonomy cases » (analogie safety cases) ; faisabilité/adoption spéculatives. Papier d'idées, pas de spec ni de code. — [F/S] [arXiv](https://arxiv.org/abs/2506.12469) ; [S] [HTML v2](https://arxiv.org/html/2506.12469v2).
- **AWS Architecture Blog, « Closing the AI agent trust gap with graduated autonomy »**, 2026-08-26 (Arora, Kezhukoot, Prabakaran). Score composite 0-100 → T1 Probation (0-40, lecture seule, tout agent démarre là), T2 Supervised (41-70), T3 Trusted (71-90), T4 Autonomous (91-100, audit a posteriori). Promotion : score maintenu sur fenêtre glissante de 50 actions + marge de 5 pts (hystérésis). Rétrogradation immédiate si sécurité sous plancher ou injection détectée. Ledger : enregistrement Think/Plan/Act/Observe/Score dans DynamoDB, état pré-action pour reprise. Révocation : politique Cedar forbid, arrêt d'urgence deny-all en secondes, redéploiement dernière version stable ; chaîne multi-agents = niveau le plus bas. Modèle conceptuel sur services AWS ; pas de dépôt/licence ni résultat terrain dans le texte lu ; poids et seuils présentés comme « template de départ ». — [F] [AWS blog](https://aws.amazon.com/blogs/architecture/closing-the-ai-agent-trust-gap-with-graduated-autonomy/). Le plus proche de la question du praticien, mais propriétaire dans sa mise en œuvre (AWS) et non portable.
- **theAuth / kavachOS (docs.theauth.dev/trust)** : score 0-100 dérivé du journal d'audit (non auto-déclaré), départ à 50, +1 par 100 appels réussis (max +25), −5 par refus, −10 par anomalie, bonus d'ancienneté (+5 >7 j, +10 >30 j) ; niveaux untrusted <40, limited 40-59, standard 60-79, trusted 80-94, elevated 95-100 (seuils codés en dur). Rétrogradation automatique non documentée, révocation non mentionnée, licence non indiquée, pas de date/version. Produit, statut de livraison et terrain non vérifiés. — [F] [docs.theauth.dev](https://docs.theauth.dev/trust) (redirigé depuis docs.kavachos.com).
- **Hermes Agent (Nous Research)** : `approvals.mode` manual / smart / off. Smart = LLM auxiliaire ; risque faible approuvé pour cette commande seule, dangereux refusé, incertain escaladé à l'humain ; timeout, refus par défaut (fail-closed) ; portées once / session / always (always → `command_allowlist` dans config.yaml, chargée au démarrage ; retirer un motif en cours de session ne s'applique qu'au redémarrage) ; `approvals.deny` globs prioritaires même en YOLO ; liste dure inamovible (rm -rf /, fork bomb) ; `hermes approvals suggest` propose des entrées d'allowlist à partir de l'historique, en lecture seule, `--apply` explicite, classes destructrices jamais proposées. Pas de journal d'audit dédié aux décisions (logs + state.db). Ouvert, livré. — [F] [doc sécurité Hermes](https://hermes-agent.nousresearch.com/docs/user-guide/security/). Contradiction de sources : cette page donne smart par défaut/timeout 300 s ; un autre résumé de la même doc (version/page différente) dit manual par défaut/60 s ([S] [résultat de recherche](https://hermes-agent.nousresearch.com/docs/guides/secure-hermes-on-a-work-machine)) — dépend de la version. Une demande de hook d'approbation personnalisé existe ([S] [issue #16475](https://github.com/NousResearch/hermes-agent/issues/16475)) ; non implémenté à notre connaissance. Meilleure illustration d'élargissement par usage (allowlist proposée depuis l'historique), mais par classe de commande shell, sans score ni démotion automatique.
- **ERC-8004 « Trustless Agents »** (Ethereum, ERC Standards Track, créé 2025-08-13, brouillon) : registres Identité / Réputation (retours score 0-100, tags, URI+hash) / Validation (attestations d'validateurs indépendants : re-exécution stake, zkML, TEE) ; déployés sur plusieurs chaînes EVM. Une étude arXiv de juin 2026 conclut que le registre tel que déployé ne fonctionne pas comme signal de confiance (enregistrements surtout factices). Ouvert, partiellement livré, terrain : critiqué. — [S] [ERC-8004 / BuildBear](https://buildbear.io/blog/erc-8004) ; [S] [arXiv 2606.26028](https://arxiv.org/abs/2606.26028) ; [S] [Polygon docs](https://docs.polygon.technology/payment-services/agentic-payments/erc8004). Réputation ≠ permissions : n'attache aucun droit.
- **Autres écrits** (non standards) : blogs « agentic autonomy is a trust score » (Monte Carlo), « progressive autonomy » (MindStudio), critères de promotion hypothétiques (score >85 % sur 60 j, 0 violation sur 30 j) d'un post Substack — [S] [Monte Carlo](https://www.montecarlodata.com/blog-agentic-autonomy-is-a-trust-score/) ; [S] [Substack](https://poojithamarreddy.substack.com/p/trust-score-architecture-the-framework) ; [S] [MindStudio](https://www.mindstudio.ai/blog/progressive-autonomy-ai-agents-safe-deployment). Opinions de praticiens ; chiffres illustratifs, pas des normes.

### Inferences
- Le mécanisme (score → niveaux, hystérésis, démotion immédiate, ledger, révocation par politique) est déjà décrit en un seul endroit (AWS) ; le vide est : format ouvert, preuves portables et vérifiables par un tiers, hors d'un cloud.
- Les chiffres de seuils varient entre sources sans base empirique : à traiter comme [H], pas comme standard.

### Gaps
- Aucune évaluation terrain publiée d'une promotion par preuves trouvée. Statut open source/licence/maturité de theAuth/kavachOS non établis. Lecture complète de Feng et al. (§certificats) et de DeepMind non faite. Pas de recherche sur les offres Okta, Google, AWS AgentCore Identity ni sur les cadres de « guardrails » (NeMo, etc.) au-delà de ce qui précède.

## Q4. Analyse des manques (matrice de couverture)

### Takeaway
Couvert : identité, délégation en chaîne, atténuation, plafonds, expiration, révocation de jeton/identité, pistes d'audit transactionnelles. Partiel : démotion sur incident, niveaux (par agent plutôt que par classe d'action), journal de preuves. Absent en standard ouvert : promotion fondée sur preuves vérifiables, exigence de réversibilité, ré-évaluation après changement de configuration, portabilité inter-éditeurs de la « réputation → droits ».

### Cited Findings (par élément ; statut = jugement de synthèse sur les sources ci-dessus)
- Promotion sur preuves : PARTIEL/propriétaire — AWS (fenêtre 50 actions, +5 pts) [F] ; theAuth (score issu de l'audit) [F] ; Hermes `approvals suggest` (propose, humain applique) [F]. Aucun standard ouvert.
- Rétrogradation sur incident : PARTIEL — AWS (immédiate, Cedar forbid) [F] ; Entra (blocage sur risque) [S] ; theAuth (via score, démotion non documentée) [F] ; DeepMind (disjoncteurs, position) [S].
- Niveaux par classe d'action : PARTIEL — Hermes (classes de commandes dangereuses, allowlist) [F] ; Niyikiza (contraintes par outil/argument) [F] ; AWS (tiers par agent : lecture/écriture/exécution) [F]. Pas de taxonomie partagée.
- Plafonds : COUVERT — AP2 budget [F], cartes [S], contraintes `range` Niyikiza [F] ; cumul dépensé = état hors jeton [NV].
- Exigence de réversibilité (action annulable avant d'élargir) : ABSENT dans les sources lues ; seulement état pré-action pour reprise chez AWS [F]. Non trouvé ailleurs.
- Registre d'audit : PARTIEL — AP2 chaîne de VDC signés [F] ; AWS DynamoDB (non portable) [F] ; Hermes sans journal dédié des décisions [F] ; theAuth audit log [F]. Aucun format commun de « preuve de fiabilité » vérifiable par un tiers, signé, qui alimente la décision.
- Révocation : COUVERT en centralisé (Entra, Mastercard, AWS) [S/F] ; PROBLÈME OUVERT pour jetons atténués hors ligne [S] ; Niyikiza §8.9 non lu.
- Ré-évaluation après changement de configuration (nouveau modèle, prompt, outils) : ABSENT dans les sources lues, sauf AWS qui redéploie la dernière version stable après échec honeypot [F]; aucune notion de « le niveau gagné ne survit pas à un changement de version » trouvée.
- Portabilité inter-éditeurs : PARTIEL/faible — OIDF recommande profils interopérables [S] ; ERC-8004 vise un registre cross-plateforme mais réputation sans droits et critiquée [S] ; AWS/Entra/cartes = verrouillés. Aucun standard de transfert de niveau entre organisations.
- Terrain : aucune des propositions de promotion/démotion sur preuves n'a de résultat publié de déploiement dans les sources lues.

### Inferences
- Test de nouveauté : le concept « autonomie qui croît avec un palmarès mesuré, démotion automatique, ledger, révocation » n'est PAS nouveau en idée (AWS 08/2026, Feng et al. 06/2025, DeepMind 02/2026, theAuth). Ce qui paraît non couvert : (1) un format ouvert et vendor-neutral liant niveau ↔ preuves ↔ classes d'actions ↔ réversibilité ; (2) invalidation/réévaluation à changement de configuration ; (3) vérification par un tiers/par l'organisation sans dépendre d'un fournisseur cloud ; (4) profil pour petites structures (sans stack AWS/Entra).
- Le risque de recouvrement le plus élevé est avec l'AWS pattern (conceptuel) et la fenêtre IETF OAuth (Niyikiza/WIMSE) si elles ajoutent un jour un mécanisme de widening ; à surveiller.

### Gaps
- Recherche de n8n/Brevo/PME et du cadre français/UE (AI Act, CNIL, normes ISO/IEC 42001) hors périmètre. Recherche exhaustive de dépôts GitHub « agent trust level » non faite : l'absence d'un standard ouvert est un constat limité à ~17 requêtes, pas une preuve d'inexistence.
